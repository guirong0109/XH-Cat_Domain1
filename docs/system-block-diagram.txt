Student (browser, React)
  |  picks major and skills / PDF CV read in the browser / goal
  v
Express API (Node 22)  ---->  BAAI/bge-m3 embedding model (local ONNX)
  |   ^                         multilingual (English + Bahasa Malaysia), not a chat LLM
  |   |                         text -> vector; closeness = cosine similarity (0 to 1)
  v   |                         used for: CV lines, skill search, role ranking, task matching
  |
  +--> 1. Role ranking (embedding search)
  |      Reference data (assumption): eMASCO role pages are taken as the official
  |      truth for what a role needs; eMASCO gives no skill importance, so we
  |      assume: specific skill = 1.5, basic skill = 1.0.
  |      Each role and each student skill/CV line becomes a vector.
  |      role similarity = mean of the 5 best-matching student lines vs the role vector
  |      -> ranked roles ("AI fit", an estimate, not a percentage)
  |
  +--> 2. Current Skill Match (fixed formula, no AI; the match is never changed by AI)
  |      credit per skill C: same skill = 1, team-reviewed similar skill = 0.5,
  |                          then x level (Basic 0.5, Good 0.8, Expert 1.0)
  |      Current Skill Match = 100 x sum(I x C) / sum(I)      I = skill importance
  |      Example: role has 2 specific skills (I=1.5) and 1 basic (I=1.0).
  |        student has skill A at Good (0.8), skill B missing (0), skill C at Expert (1.0)
  |        = 100 x (1.5x0.8 + 1.5x0 + 1.0x1.0) / (1.5 + 1.5 + 1.0) = 100 x 2.2 / 4.0 = 55%
  |
  +--> 3. AI exposure of a role (shown beside the match, never part of it)
         a) eMASCO tasks of the role are matched to O*NET tasks by bge-m3
            (keep cosine >= 0.80; need at least 3 matched tasks, else "not enough data")
         b) Anthropic Economic Index gives observed AI use per O*NET task (0 to 1)
         c) role AI use = average over its matched tasks
         d) tasks are classified in three categories:
              Automatable   = AI can do the task itself
              AI-assisted   = AI helps, the person still decides
              Human-led     = needs people (judgement, care, presenting)
            observed AI use covers the matched tasks; the AI-made labels
            (labelled "estimate") cover the rest:
            automatable % = w x observed share + (1 - w) x label,  w = matched / total tasks
         e) Job outlook = 0.5 x demand (OpenDOSM) + 0.5 x (100 - automatable % x scenario)
            scenario: Moderate 0.6, Fast 1.0

=====================================================================
PART B. HOW SEARCH WORKS (skill search and role search; runs on our own saved data)
=====================================================================
Note: there is no external Search API or database server. "Search" means searching the
eMASCO data we already saved (18,161 skills, 1,814 roles) with four rankers, then merging.

Student types a skill ("accounting", "perakaunan") or uploads a CV
  |
  v
GET /api/emasco/skills?q=...   (query max 100 characters, max 20 results, cached)
  |
  +--> Ranker 1  EXACT     every typed word is inside the skill text (good for "c++", codes)
  +--> Ranker 2  BM25      any word counts; rare words weigh more (partial matches)
  +--> Ranker 3  CONCEPT   query names one of our team skills or aliases (English + Malay)
  +--> Ranker 4  MEANING   bge-m3 vector of the query vs the saved skill vectors
  |                        (finds synonyms and Malay); kept only if cosine >= 0.55 and
  |                        within 0.08 of the best hit (stops unrelated matches)
  v
Merge by Reciprocal Rank Fusion:  score(skill) = sum over rankers of 1 / (60 + rank)
  (uses ranks only, so scores from different rankers are never compared)
  |
  v
Optional reranker re-orders the top results  ->  top 20 skills shown
  If the model is off (Replit), MEANING and rerank are skipped and the reply says so.

Role search (POST /api/matches/top and /api/emasco/match):
  picked skills or CV lines -> vectors -> cosine vs every role vector
  role similarity = mean of the 5 best-matching lines
  -> diploma-level filter -> merge grades -> split into "your field" / "other fields" lists
  CV lines: keyword match is added at once; an AI match (cosine >= 0.72) waits for the student's "Add skill"
  CV text is never stored or logged.


=====================================================================
PART C. HOW DATA IS SAVED (no database server: JSON files, written safely)
=====================================================================
Source (official or open API)
  |  fetch with retries, 8 s timeout, error kinds (rate limit, timeout, bad reply)
  v
Validate the reply (shape, numbers, row counts; all-or-nothing)
  |  fail -> keep the LAST GOOD file, record the failure, show its old date
  v
Write to a temporary file, then rename over the real file (atomic; no half-written data)
  |  only one refresh of the same file runs at a time (single in-flight)
  v
Saved JSON with source, fetched date and count:
  data/trends.json        OpenDOSM job trend per occupation group
  data/research.json      AI-research counts per skill (OpenAlex)
  data/references.json    eMASCO page check and link check per role
  data/course_checks.json HRD Corp / MyTVET course page checks
  data/exposure.json      observed AI use per role (built from embeddings, see PART A step 3)
  data/emerging.json      reviewed news items (information only)
  data/emasco/            1,814 roles + skill/role vectors (int8, committed)
  data/skills/, data/intel/  skill catalogue with quoted evidence; one versioned record per role
  data/store/             manifest of every dataset + AI-exposure file for every role
Generated files are rebuilt by scripts, never edited by hand. Team-written inputs are in
data/team/ and are labelled "draft" until a teammate reviews them.


=====================================================================
PART D. HOW DATA IS MAINTAINED (automatic refresh, monitoring, human review)
=====================================================================
Triggers
  weekly GitHub Action (Mondays 02:00 UTC): trends, research, references, course checks
                                            -> commits only if a file changed -> main -> Replit
  "Refresh data" button on Matches          -> POST /api/refresh-trends | research | references
  Emerging feed: weekly by default (daily by setting), or admin refresh
  New Anthropic release (admin page shows "new data") -> re-run embed + match + build-exposure
  eMASCO changes: quick check (about 3 min) and full re-check (about 3 h, resumable) on /admin

Monitoring (server/sources/monitor.js, shown on /admin "Data sources")
  every call to every source is recorded: last success, failures in a row, rate-limit hits, speed
  status: ok -> warning -> DOWN after 3 failures in a row; STALE if no success for 8 days
  a failing source never blocks the app: the last good data stays and shows its date

Rules that protect the data
  - a check only REPORTS; a role that eMASCO changed is flagged for the team, never overwritten
  - skill dataset and intelligence builds are incremental by input hash, idempotent, validated
    before writing, and keep the previous copy; intelligence keeps the last 50 runs
  - Emerging items start "Pending review"; the admin approves; new sources only by the admin
    after a feed test and a "read the publisher terms" tick
  - no signal enters a score unless its source is in server/sources/registry.js with a date,
    a failure monitor and a fallback; ILO, OECD, research and Emerging never change the score
  - keys come only from environment variables, are never committed or logged

Human review (the maintenance that cannot be automated)
  teammate reviews the drafts: role skills, SDG tags, aliases, similar-skill pairs,
  course pages, judged task pairs; 31 of 122 role-skill rows are "not listed" (review item)


=====================================================================
PART E. "EMERGING THIS WEEK" FEED (information only; never part of any score)
=====================================================================
Purpose: show the student real, recent headlines about AI and work, so they see what is
changing now. It does not change a score, role, skill or label. The card says "Not part of the score".

TRIGGER   weekly by default (daily by setting), "Refresh now" in /admin, or script refresh-emerging.ps1
  |       public route POST /api/refresh-emerging needs an admin token; without ?force=1 it returns
  |       the saved file while it is still fresh (7 days; 20 hours in daily mode)
  v
1. COLLECT (how it searches: public feeds and open APIs only; no scraping, no search API, no job-ad sites)
     OpenAlex works API   query: ("artificial intelligence" OR "generative AI" OR "machine learning")
                          AND (jobs OR skills OR workforce OR employment OR automation)
                          last 30 days; English, Malay or Chinese only
     RSS news feeds (9 built in; admin can add more):
        English: MIT News AI, MIT Technology Review, Free Malaysia Today, Malay Mail Money
        Malay:   Berita Harian, Astro Awani Business, FMT Bahasa
        Chinese: BBC Chinese, DW Chinese
     fetch: 8 s timeout, robots.txt respected; a source that fails is skipped, the rest still run
  |
  v
2. FILTER (rules, no AI)
     topic feeds: pass if an AI word OR a work word is in the title/snippet
     general news feeds: must contain a WORK word (jobs, skills, hiring, layoffs, automation;
       Malay: kerja, pekerja, gaji, kemahiran; Chinese: 工作, 就业, 技能, 裁员 ...), so stock-market stories drop out
     drop: future dates, older than 30 days, duplicates (same address or same title), addresses
       the admin deleted before (removedUrls); at most 10 new items per source, 40 per run
  |
  v
3. CLASSIFY (one batched model call for all new items; the only generative-model use in the app)
     input: title + snippet only (no full article)
     asked for each item, as JSON only:
        fields   zero or more role groups from data/fields.json, else "General"   (the category)
        skills   up to 3 skill names; a name from our skill list is "in eMASCO", a new name is
                 marked "Emerging, not in eMASCO" (allowed only if the title clearly names it)
        summary  one English sentence, max about 200 characters, labelled "AI estimate"
     the reply is VALIDATED: unknown fields or malformed items are dropped
     main model, then a backup model only if the main one fails; model and key come from
       environment variables (never committed or logged)
     no model or both fail: KEYWORD fallback (tags by matching skill words, no summary)
     confidence is set by the SOURCE type, never by the AI: OpenAlex = High, news feeds = Medium
  |
  v
4. SAVE (same safe-save rules as PART C)
     data/emerging.json  per item: title, real source link, source name, language, published date,
       checked date, confidence, fields, skills, summary, review = "pending"
     written atomically under a lock, so an admin review made during a refresh is not lost
     a failed refresh keeps the last good file and says so
  |
  v
5. HUMAN REVIEW (the admin on /admin, this PC only)
     items start "Pending review"; the admin checks the link, the date, the category and the
       summary, then marks "Reviewed by the team", puts it back to pending, or deletes it
     sources table: last run per source, switch a source off or on, remove a source you added
     add a source: name, https feed address, language, filter -> "Test this feed" (reads robots.txt
       and the first headlines) -> tick "I read the publisher terms" -> server tests again -> Add
       (https only; no IP or local names; no redirects; 2 MB cap; at most 20 added)
  |
  v
6. SHOW (Matches page, under "Skills in demand")
     each item: headline link, source, published and checked dates, confidence badge,
       review badge (Pending review / Reviewed by the team), role-group tags,
       "Emerging, not in eMASCO" for new skills, Malay / Chinese badge, "AI estimate:" summary
     card hidden until a first refresh has saved the file; "No new items this week" if empty

Limits stated openly: the filter is loose (some items are not about jobs, so the admin deletes them);
summaries use only the title and snippet; reviews live in data/emerging.json on the admin's PC
(not committed, so Replit shows nothing until a reviewed file is committed); the team has not
yet read the publisher terms.
